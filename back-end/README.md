# Backend — dbt Lineage Explorer API

FastAPI service that reads dbt artifacts (`manifest.json` + `catalog.json`) and serves the
lineage graph, per-model details and fuzzy search. Managed with [uv](https://docs.astral.sh/uv/).

## Quick start

```bash
cd back-end
uv sync --group dev          # create .venv and install everything
uv run lineage-api --reload  # http://127.0.0.1:8000  (docs at /docs)
```

Alternatively: `uv run uvicorn app.main:app --reload --port 8000`

## Tests

```bash
uv run pytest          # unit + contract tests against fixtures/
uv run ruff check .
```

## Configuration

A **pipeline is one dbt project** with its own `manifest.json` + `catalog.json`, laid out as
`models/01_source` → `02_intermediate` → `03_output` (src / int / out). The pipelines to load
are listed in a YAML file; relative paths resolve against the YAML's folder. `name` is
required. It identifies the pipeline, because all dbt projects share the `project_name`
`dbt_pnc`, and node ids are scoped by it (`model.dbt_pnc.x` → `model.<name>.x`):

```yaml
# pipelines.yaml
pipelines:
  - name: bestand_mfp
    dir: bestand_mfp                          # manifest.json (+ catalog.json) inside
  - name: schaden_claims
    manifest: ~/pnc/claims/target/manifest.json
    catalog: ~/pnc/claims/target/catalog.json   # optional
```

Pipelines read each other's outputs through dbt sources. The loader links such a source to
the model with the **same table name** in another pipeline, ignoring database and dataset.
Output table names are assumed unique (details: `../contract.md` §1.0).

| Variable | Default | Purpose |
|---|---|---|
| `PIPELINES_CONFIG` | `../fixtures/pipelines.yaml` | the pipelines YAML above |
| `BQ_CONSOLE_PROJECT` | node's `database` | GCP project used for BigQuery deeplinks |
| `CORS_ORIGINS` | Vite dev servers | comma-separated allowed origins |

```bash
PIPELINES_CONFIG=~/pnc/pipelines.yaml uv run lineage-api
```

After a fresh `dbt docs generate` you can reload without a restart: `curl -X POST localhost:8000/api/reload`.

## Endpoints

| Method | Path | Notes |
|---|---|---|
| `GET` | `/api/health` | loaded artifacts, node count |
| `GET` | `/api/meta` | pipelines, stages, materializations, tags |
| `GET` | `/api/graph` | `?pipeline=…&stage=…&include_sources=false` |
| `GET` | `/api/model/{id}` | dbt `unique_id` **or** plain model name |
| `GET` | `/api/search?q=…` | typo-tolerant, rapidfuzz |
| `GET` | `/api/search/columns?q=…` | column search (feature 2.2) |
| `GET` | `/api/lineage/column?model=…&column=…&direction=up\|down\|both` | column-level lineage (2.3) |
| `GET` | `/api/lineage/status` | per-model SQL parse status and coverage (2.3) |
| `POST` | `/api/reload` | re-read artifacts from disk |

The payload shapes are fixed in [`../contract.md`](../contract.md) and typed in
`app/schemas.py` (Pydantic) / `../front-end/src/api/types.ts` (TypeScript).

## Layout

```
app/
├── config.py    env settings + stage convention (src/int/out)
├── loader.py    manifest+catalog -> internal graph (pure data, no FastAPI)
├── service.py   GraphService: contract responses, BQ deeplinks, dbt run command
├── search.py    fuzzy scoring (rapidfuzz, difflib fallback)
└── main.py      FastAPI routes + CORS
tests/           loader unit tests + HTTP contract tests
```

## Fixtures

`../fixtures/` holds a synthetic PnC setup generated by `../fixtures/generate_fixtures.py`:
two pipelines as separate dbt projects (`bestand_mfp/`, `schaden_claims/`, each with its own
manifest + catalog, 23 models in total), with `schaden_claims` importing three
`bestand_mfp` outputs as sources. `pipelines.yaml` lists both. For a performance check:

```bash
python3 ../fixtures/generate_fixtures.py --scale 30 --out-dir /tmp/big   # 60 pipelines
PIPELINES_CONFIG=/tmp/big/pipelines.yaml uv run lineage-api
```
